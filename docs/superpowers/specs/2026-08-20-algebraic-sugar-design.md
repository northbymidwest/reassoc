# algebraic-sugar: design

**Status:** approved for implementation
**Date:** 2026-08-20
**MSRV:** 1.98 (algebraic float operators stabilized)

## Summary

`algebraic-sugar` lets you write ordinary arithmetic syntax (`a * b + c`) and
have it compile to Rust 1.98's algebraic float operators (`algebraic_add`,
`algebraic_sub`, `algebraic_mul`, `algebraic_div`, `algebraic_rem`), which
permit reassociation and FMA contraction.

Two entry points share one rewriter:

```rust
let e = alg!(a * b + c);       // fine-grained, expression scope

#[algebraic]                    // wholesale, item scope
fn kernel(a: &[f32], b: &[f32]) -> f32 { /* ... */ }
```

## Motivation

Measured on aarch64 at `-O`, a dot product loop:

| version | codegen |
| --- | --- |
| plain `+`/`*` | 21x scalar `fadd s0` — serial dependency chain, no reassociation |
| algebraic ops | 8x `fmla.4s`/`fadd.4s` — fully vectorized, FMA-contracted |

Writing `s.algebraic_add(a[i].algebraic_mul(b[i]))` by hand gets this, but the
method-call form is unreadable for anything larger than a single expression.

## Non-goals

- Unary negation. There is no `algebraic_neg` in 1.98 (verified); `-x` is left
  untouched.
- Rewriting inside macro invocations other than `plain!`. The proc macro runs
  before macro expansion and cannot see through `assert_eq!`/`println!` bodies.
  Documented limitation.
- `#[algebraic]` on `impl` blocks and `mod`s. Deferred until there is demand.
- Nightly specialization. Everything here works on stable.

## Architecture

Two crates; users depend only on the facade.

- **`algebraic-sugar`** — `no_std` facade. Owns the dispatch traits, their
  impls, `passthrough!`, `plain!`, and re-exports the proc macros.
- **`algebraic-sugar-macros`** — proc macro crate (`syn`, `quote`,
  `proc-macro2`). Owns `alg!` and `#[algebraic]`, sharing one rewriter module.

## The dispatch layer

A proc macro sees syntax, not types. Given `a * b` it cannot know whether `a`
is `f32` or `usize`, so it cannot emit `a.algebraic_mul(b)` directly without
breaking all integer arithmetic in annotated code. Instead it emits a call into
a dispatch layer whose implementation the *type checker* selects:

```rust
a * b   ->   ::algebraic_sugar::mul(a, b)
```

### Trait shape (load-bearing)

The output is a **type parameter**, not an associated type:

```rust
pub trait AlgMul<B, O> { fn a_mul(self, b: B) -> O; }

#[inline(always)]
pub fn mul<A: AlgMul<B, O>, B, O>(a: A, b: B) -> O { a.a_mul(b) }
```

This is not a stylistic choice. Two alternatives were built and rejected
against the compiler:

1. **Autoref specialization** (`impl AlgMul for &&Op<f32,f32>` + blanket
   fallback on `&Op<A,B>`). Method resolution must know the receiver type
   eagerly, so `let s = 0.0; ... -> f32` defaults the literal to `f64` and then
   fails with a cryptic `E0271`.
2. **Associated output type** (`trait AlgMul<Rhs> { type Out; }`). Same
   failure: rustc cannot invert the projection `<A as AlgMul>::Out == f32` to
   determine `A`, so unannotated literals default and error.

With `O` as a type parameter, `O` unifies directly with the expected return
type and inference flows backwards. Verified passing: unannotated float
accumulators, unannotated integers, reference operands, `Duration * u32`,
loop accumulators, and iterator closures over `&f32`.

### Zero cost

Verified, not assumed. At `-O`, rustc emits `_dot_outparam = _dot_direct` —
the dispatched version is byte-identical to hand-written algebraic calls and is
merged into the same symbol. No wrapper struct and no call survives.

Debug builds (`-C opt-level=0`) do carry overhead from un-inlined generic calls.
Correctness is unaffected; this is documented, not fixed.

### Coverage

Impls are enumerated (generated by `macro_rules!`), not blanket:

| category | dispatch | gating |
| --- | --- | --- |
| `f32`, `f64` | algebraic ops | core |
| all integer types | plain `std::ops` | core |
| all reference combinations of the above | as above, auto-deref | core |
| `core::time::Duration` heterogeneous pairs | plain | core |
| `String + &str` | plain | `alloc` feature |
| `Instant`, `SystemTime` | plain | `std` feature |
| user-defined types | plain | one-line `passthrough!` |

**Why user types cannot be automatic.** Full coverage would need
`impl<A: Add<B, Output=O>, B, O> AlgAdd<B, O> for A`, which overlaps the
`f32`/`f64` impls. Stable Rust has no specialization to break the tie. This is
a language limitation. The cost is one line per type, once:

```rust
algebraic_sugar::passthrough!(Vec3);
algebraic_sugar::passthrough!(Duration, u32 => Duration);
```

The compiler points the user straight at it via
`#[diagnostic::on_unimplemented]` (stable since 1.78):

```
error[E0277]: `Vec3` can't be used with arithmetic inside an `#[algebraic]` scope
   = note: wrap this expression in `plain!(..)` to use ordinary operators,
   = note: or opt the type in once with `algebraic_sugar::passthrough!(Vec3);`
```

## Macro surface

### `alg!(expr)`
Rewrites arithmetic operators in a single expression. Returns the expression's
value.

### `#[algebraic]`
Rewrites a function body. Scope is configurable:

| form | behavior |
| --- | --- |
| `#[algebraic]` | body + closure bodies; stops at nested `fn`/`impl`/`mod` (default) |
| `#[algebraic(deep)]` | also descends into nested items |
| `#[algebraic(shallow)]` | body statements only; closure bodies untouched |
| `#[algebraic(skip)]` | on a nested item, excludes it from an enclosing `deep` |

### `plain!(expr)`
Marks a subtree as strictly IEEE. The rewriter emits its contents verbatim and
does not descend. Defined as an identity macro so it also compiles outside an
annotated scope.

Its purpose is *not* type coverage — it protects code that depends on exact
rounding. Compensated summation is the motivating case:

```rust
c = plain!((t - sum) - y);   // algebraically zero; reassociation would delete it
```

### `passthrough!(Ty)` / `passthrough!(A, B => Out)`
Generates the five dispatch impls for a type using its `std::ops`
implementations.

## Rewrite rules

- Binary `+ - * / %` become `sugar::{add,sub,mul,div,rem}` calls.
- Compound assignment `+= -= *= /= %=` becomes a read-modify-write. Place
  expressions are bound once through a temporary to preserve evaluation
  semantics:
  ```rust
  v[f()] += x;
  // ->
  { let __p = &mut v[f()]; *__p = sugar::add(*__p, x); }
  ```
  Without this, `f()` would be evaluated twice.
- Unary `-` untouched (no `algebraic_neg`).
- `plain!(..)` contents emitted verbatim, no descent.
- Other macro invocations not descended into.
- Spans are preserved so type errors point at the original operator.

## Testing strategy

**Assembly-level dispatch guard — required, not optional.** During design, a
shim with inverted autoref priority sent `f32` down the *plain* path. It
compiled cleanly and returned numerically correct results; only reading the
assembly caught it (`_dot_shim = _dot_plain`). Behavioral tests cannot detect
this class of bug, because algebraic and plain ops agree on most inputs.

The suite therefore includes a test that compiles a fixture with
`-O --emit asm` and asserts vector FMA instructions are present in a dot-product
kernel. Gated to `x86_64` and `aarch64`.

Also:
- `trybuild` UI tests pinning the `on_unimplemented` diagnostics.
- Inference regression tests: unannotated accumulators, integers, references,
  heterogeneous pairs — each a case that a wrong trait shape would break.
- Compound-assignment side-effect test asserting single evaluation.
- Scope tests for `deep` / `shallow` / `skip`.
- A `no_std` build target in CI, plus `--no-default-features`.

## Risks

| risk | mitigation |
| --- | --- |
| Silent dispatch to plain ops | asm-level test in CI |
| Debug-build overhead | documented |
| Macro bodies not rewritten | documented; `alg!` usable inside them |
| User types need opt-in | `on_unimplemented` names the fix |
