# reassoc: design

> **Historical. Superseded, and wrong about the crate as it stands.**
>
> This is the design as it was approved on 2026-08-20, before any of it was
> built. It describes one trait per operator (`AlgAdd<B, O>`, method
> `alg_add`), keyed on the *left* operand. The crate replaced that in 0.3.0
> with a pair of traits per operator keyed on the right operand
> (`AddRhs<Lhs, O, Tag>`), because a left-keyed trait makes two opt-ins for
> one type overlap and `passthrough!(mul: Vec3, f32 => Vec3)` inexpressible.
> Nothing named `Alg*` exists any more.
>
> Kept because the reasoning that was later overturned is worth being able
> to read. For what the crate actually does, see
> [`docs/design.md`](../../design.md), and `CLAUDE.md` for the one-line rule
> behind each shape.

**Status:** superseded by the implementation; see the note above
**Date:** 2026-08-20
**MSRV:** 1.98 (algebraic float operators stabilized)

## Summary

`reassoc` lets you write ordinary arithmetic syntax (`a * b + c`) and
have it compile to Rust 1.98's algebraic float operators (`algebraic_add`,
`algebraic_sub`, `algebraic_mul`, `algebraic_div`, `algebraic_rem`), which
permit reassociation and FMA contraction.

Two entry points share one rewriter:

```rust
let e = alg!(a * b + c);       // fine-grained, expression scope

#[algebraic]                    // wholesale, item scope
fn kernel(a: &[f32], b: &[f32]) -> f32 { /* ... */ }
```

## Motivation

Measured on aarch64 at `-O`, a dot product loop:

| version | codegen |
| --- | --- |
| plain `+`/`*` | 21x scalar `fadd s0`, a serial dependency chain, no reassociation |
| algebraic ops | 8x `fmla.4s`/`fadd.4s`, fully vectorized, FMA-contracted |

Writing `s.algebraic_add(a[i].algebraic_mul(b[i]))` by hand gets this, but the
method-call form is unreadable for anything larger than a single expression.

## Non-goals

- Unary negation. There is no `algebraic_neg` in 1.98 (verified); `-x` is left
  untouched.
- Rewriting inside **any** macro invocation. The proc macro runs before macro
  expansion and cannot see through a macro's token stream at all. This is why
  `strict!` works without being special-cased. Documented limitation.
- `#[algebraic]` on `impl` blocks and `mod`s. Deferred until there is demand.
- Nightly specialization. Everything here works on stable.

## Architecture

Two crates; users depend only on the facade.

- **`reassoc`**: `no_std` facade. Owns the dispatch traits, their
  impls, `passthrough!`, `strict!`, and re-exports the proc macros.
- **`reassoc-macros`**: proc macro crate (`syn`, `quote`,
  `proc-macro2`). Owns `alg!` and `#[algebraic]`, sharing one rewriter module.

## The dispatch layer

A proc macro sees syntax, not types. Given `a * b` it cannot know whether `a`
is `f32` or `usize`, so it cannot emit `a.algebraic_mul(b)` directly without
breaking all integer arithmetic in annotated code. Instead it emits a call into
a dispatch layer whose implementation the *type checker* selects:

```rust
a * b   ->   ::reassoc::ops::mul(a, b)
```

### Trait shape (load-bearing)

The output is a **type parameter**, not an associated type:

```rust
pub trait AlgMul<B, O> { fn alg_mul(self, rhs: B) -> O; }

#[inline(always)]
pub fn mul<A: AlgMul<B, O>, B, O>(a: A, b: B) -> O { a.alg_mul(b) }
```

This is not a stylistic choice. Two alternatives were built and rejected
against the compiler:

1. **Autoref specialization** (`impl AlgMul for &&Op<f32,f32>` + blanket
   fallback on `&Op<A,B>`). Method resolution must know the receiver type
   eagerly, so `let s = 0.0; ... -> f32` defaults the literal to `f64` and then
   fails with a cryptic `E0271`.
2. **Associated output type** (`trait AlgMul<Rhs> { type Out; }`). Same
   failure: rustc cannot invert the projection `<A as AlgMul>::Out == f32` to
   determine `A`, so unannotated literals default and error.

With `O` as a type parameter, `O` unifies directly with the expected return
type and inference flows backwards. Verified passing: unannotated float
accumulators, unannotated integers, reference operands, `Duration * u32`,
loop accumulators, and iterator closures over `&f32`.

### Zero cost

Verified, not assumed. At `-O`, rustc emits `_dot_outparam = _dot_direct`,
the dispatched version is byte-identical to hand-written algebraic calls and is
merged into the same symbol. No wrapper struct and no call survives.

Debug builds (`-C opt-level=0`) do carry overhead from un-inlined generic calls.
Correctness is unaffected; this is documented, not fixed.

### Coverage

Impls are enumerated (generated by `macro_rules!`), not blanket:

| category | dispatch | gating |
| --- | --- | --- |
| `f32`, `f64` | algebraic ops | core |
| all integer types | plain `std::ops` | core |
| all reference combinations of the above | as above, auto-deref | core |
| `core::time::Duration` heterogeneous pairs | plain | core |
| `String + &str` | plain | `alloc` feature |
| `Instant`, `SystemTime` | plain | `std` feature |
| user-defined types | plain | one-line `passthrough!` |

**Why user types cannot be automatic.** Full coverage would need
`impl<A: Add<B, Output=O>, B, O> AlgAdd<B, O> for A`, which overlaps the
`f32`/`f64` impls. Stable Rust has no specialization to break the tie. This is
a language limitation. The cost is one line per type, once:

```rust
reassoc::passthrough!(Vec3);
reassoc::passthrough!(mul: MyScalar, u32 => MyScalar);
```

The compiler points the user straight at it via
`#[diagnostic::on_unimplemented]` (stable since 1.78):

```
error[E0277]: `Vec3` can't be used with arithmetic inside an `#[algebraic]` scope
   = note: wrap this expression in `strict!(..)` to use ordinary operators,
   = note: or opt the type in once with `reassoc::passthrough!(Vec3);`
```

## Macro surface

### `alg!(expr)`
Rewrites arithmetic operators in a single expression. Returns the expression's
value.

### `#[algebraic]`
Rewrites a function body. Scope is controlled by two independent named
parameters, because closures and nested items are separate axes and a single
linear scale cannot express every useful combination.

| parameter | default | effect when set |
| --- | --- | --- |
| `closures` | `true` | `false` leaves closure bodies untouched |
| `items` | `false` | `true` descends into nested `fn`/`impl`/`mod` |
| `skip` | n/a | bare flag on a nested item; excludes it from an enclosing `items = true` |

```rust
#[algebraic]                                  // closures yes, items no
#[algebraic(closures = false)]                // skip closure bodies
#[algebraic(items = true)]                    // descend into nested fns
#[algebraic(closures = false, items = true)]  // both axes, independently

#[algebraic(skip)]                            // opt a nested item back out
fn strict_helper(x: f32) -> f32 { x * x }
```

Defaults are chosen so the common case needs no parameters: closure bodies are
usually where the hot numeric kernel lives, while a nested `fn` reads like a
standalone item and should opt in explicitly.

Unknown parameters are a compile error, not silently ignored.

### `strict!(expr)`
Marks a subtree as strictly IEEE. It is an ordinary identity macro: the
rewriter does not recognize it by name or special-case it in any way. Its
contents keep ordinary operator semantics purely because the rewriter never
descends into a macro invocation.

Consequently `strict!` must be in scope like any macro, either imported or
path-qualified. An earlier design consumed it during rewriting, which made the
natural `use reassoc::{algebraic, strict};` spelling emit an unused-import
warning, a hard error under `#![deny(warnings)]`. Defined as an identity macro so it also compiles outside an
annotated scope.

Its purpose is *not* type coverage: it protects code that depends on exact
rounding. Compensated summation is the motivating case:

```rust
c = strict!((t - sum) - y);   // algebraically zero; reassociation would delete it
```

### `passthrough!`
Opts a type into the dispatch layer using its existing `std::ops` impls.

```rust
passthrough!(Vec3);                          // all five ops, same-type
passthrough!(mul: MyScalar, u32 => MyScalar); // one op, heterogeneous
```

The same-type form generates all five impls. The heterogeneous form names a
single operator, because heterogeneous types rarely implement all five;
`Duration * u32` exists, `Duration + u32` does not.

## Rewrite rules

- Binary `+ - * / %` become `::reassoc::ops::{add,sub,mul,div,rem}` calls,
  always via the absolute path so the macros work regardless of what is in scope.
- Compound assignment `+= -= *= /= %=` becomes a read-modify-write. **The
  right-hand side is bound first**, then the place, matching Rust's own
  RHS-then-place evaluation order for primitive `+=`:
  ```rust
  v[f()] += g();
  // ->
  {
      let __rhs = g();
      let __p = &mut v[f()];
      *__p = ::reassoc::ops::add(*__p, __rhs);
  }
  ```
  Binding the place once prevents `f()` from being evaluated twice. Binding the
  RHS *first* is equally load-bearing: taking `&mut` on the place before
  evaluating the RHS makes any RHS that reads the place fail to borrow-check,
  rejecting valid code such as `s += s * k` (an EMA accumulator) and
  `a[0] += a[1]` (an FFT butterfly).
- Const positions are never rewritten: the `len` of an array-repeat
  expression, and `const`/`static` items. `::reassoc::ops::*` are not
  `const fn`, so rewriting there would fail with `E0015` blamed on the
  attribute. `#[algebraic]` on a `const fn` is rejected with an authored
  error.
- Unary `-` becomes `::reassoc::ops::neg`, a same-type function over a blanket
  `Neg` impl. There is still no `algebraic_neg`; the indirection exists purely
  so the expected type flows backwards into the operand. Without it,
  `alg!(-(3.0 * 2.0))` fails with `E0282`: the operand is a rewritten call
  whose type is an inference variable, and `Neg` has nothing to resolve
  against. Not applied over a literal: `-128i8` would become `neg(128i8)`,
  and `128` does not fit in an `i8`.
- No macro invocation is descended into, `strict!` included. Nothing is
  matched by name.
- Spans are preserved so type errors point at the original operator.

## Testing strategy

**Assembly-level dispatch guard, required not optional.** During design, a
shim with inverted autoref priority sent `f32` down the *plain* path. It
compiled cleanly and returned numerically correct results; only reading the
assembly caught it (`_dot_shim = _dot_plain`). Behavioral tests cannot detect
this class of bug, because algebraic and plain ops agree on most inputs.

The suite therefore includes a test that compiles a fixture with
`-O --emit asm` and asserts vector FMA instructions are present in a dot-product
kernel. Gated to `x86_64` and `aarch64`.

Also:
- `trybuild` UI tests pinning the `on_unimplemented` diagnostics.
- Inference regression tests: unannotated accumulators, integers, references,
  heterogeneous pairs, each a case that a wrong trait shape would break.
- Compound-assignment side-effect test asserting single evaluation.
- Scope tests covering all four `closures`/`items` combinations, `skip`,
  and rejection of unknown parameters.
- A `no_std` build target in CI, plus `--no-default-features`.

## Risks

| risk | mitigation |
| --- | --- |
| Silent dispatch to plain ops | asm-level test in CI |
| Debug-build overhead | documented |
| Macro bodies not rewritten | documented; `alg!` usable inside them |
| User types need opt-in | `on_unimplemented` names the fix |
